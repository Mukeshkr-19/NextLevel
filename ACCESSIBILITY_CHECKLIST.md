# Accessibility Checklist

Use this checklist before public-facing pages are considered ready for event use. The practical target is WCAG-style AA review, but this checklist is not a legal compliance claim.

## Public-facing pages

Review these pages before demo or event use:

- home page,
- login page,
- game page,
- leaderboard,
- mentor and staff pages,
- conference/gallery pages.

## Page structure

- The page has one clear main heading.
- Headings are nested in a logical order.
- Navigation links have clear names.
- The page title describes the page.
- Important content is not hidden behind hover-only interactions.

## Keyboard access

- All links, buttons, forms, and menus can be reached by keyboard.
- Focus order follows the visible page order.
- Focus is visible on every interactive element.
- There are no keyboard traps.
- Forms can be submitted without a mouse.

## Forms

- Every input has a visible label.
- Error messages explain what to fix.
- Required fields are clear.
- Buttons say what action they perform.
- Placeholder text is not the only label.

## Images and media

- Informational images have meaningful alt text.
- Decorative images use empty alt text.
- Photo gallery changes need extra review before release.
- No autoplaying or distracting motion is added unless users can pause it.

## Color and layout

- Text has enough contrast against its background.
- Information is not communicated by color alone.
- Text remains readable when zoomed.
- Content works on laptop, projector, tablet, and phone widths.
- Text does not overlap or get cut off.

## Live leaderboard

- Leaderboard updates should not be too visually distracting.
- Rank, team name, and points should be readable from a projector.
- Do not rely only on animation or color to show changes.
- If screen reader behavior becomes important for public use, review live-update announcements separately.

## EDI guidance boundary

Do not share the code or project files externally. If asking EDI for guidance, ask general questions only, such as:

```text
For an event website with forms, a live leaderboard, and a photo gallery, what accessibility issues should we review before student participants use it?
```

## Review result wording

Use careful wording:

- `accessibility-reviewed`,
- `checked against project accessibility checklist`,
- `needs general accessibility guidance`,
- `needs more review before public event use`.

Avoid claiming legal ADA compliance unless the proper reviewer has confirmed it.
